# AIC 手势控制最小实现方案

实现进度：电脑端预览 v0.1.0 已加入本仓库，使用方法与当前验证范围见 [README](../README.md)。为简化安装，首版采用 MediaPipe 0.10.21 随包提供模型的 `solutions.hands`；Tasks Hand Landmarker 保留为后续可替换的识别接口。

## 推荐结论

先在现有电脑上做手部识别，复用 AIC 原六轴姿态控制的机器人执行链路。第一版只需电脑现有摄像头和机器人原有智慧背包，不增加传感器，不训练模型。

先跑通“单手控制一个肘关节”，再扩展为“双手分别控制左右臂，每只手控制三个上肢关节”。这是连续控制：手移动多少、手指开合多少，对应关节目标就改变多少。

MLKPAI-FS01 是可选的后续移植目标。按照 AIC 最近一次板卡接续记录，它尚未完成 Linux 启动恢复，摄像头出图也未验证；将它放进第一版的必需链路会增加启动、驱动和模型部署工作。后续状态如果已变化，再据现场结果调整。

## 已查到的项目事实

本轮读取了 AIC 项目中以下对话的消息和历史源文件读取输出：

- 《查看新板卡和摄像头用法》：新板卡是米联派 MLKPAI-FS01，DR1M90M、20250512 版，配 MLK-CAM001 V1.0 摄像头。最新接续记录为 USB 下载通道已通，Linux 启动恢复未完成；DDR 配置疑似不匹配，不能据此判定板卡损坏。
- 《升级项目功能冲刺国赛》：功能一最终包为 `backpack_arms6.zip`，原实现是电脑 OpenCV + MediaPipe PoseLandmarker、本地六轴几何计算、TCP 8765 发送、智慧背包标定与限速、UART 驱动机器人。
- 同一对话中的 `robot_final` README、技术说明、`vision_capture.py` 和 `arm_config.json` 读取输出，进一步给出了六轴标定、共享串口和停止行为。

原实时六轴跟随与后来录制/回放合并版需区分：实时跟随使用 TCP 8765；`robot_final` 使用 TCP 8767，且其中的摄像头目前只录制动作，不直接实时驱动。因此优先从 `backpack_arms6` 派生手势跟随功能；以后需要接统一窗口时，再适配合并版。

机器人背包的输出串口是 `/dev/ttyS0`，115200、8E1。此前修复的 CP2104 USB 串口属于 IMU 输入，不能把它当作这次的舵机输出接口。

这些是方案调研时读取的历史资料证据。尚未重新读取 Windows 项目的完整控制源码，也没有连接实际机器人；方案调研开始时，云端仓库只有一个 README。

## 手部识别选择

继续使用 Python、OpenCV、MediaPipe 技术路线。实际首版建立独立 `.venv`，使用 MediaPipe 0.10.21 自带的完整手部模型，输出每只手的 21 个关键点和左右手分类。若以后改用 Tasks Hand Landmarker，需要新增对应模型资源并适配 API。

使用关键点计算连续控制量即可，不需要先训练“握拳、剪刀手”等手势分类器，也不需要人体全身入镜。

参考：[Google 官方 Hand Landmarker 文档](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker?tab=Python)。实际运行速度需在用户这台电脑上测量。

## 分两步实现关节控制

### 第一步：一只手控制一个肘关节

先选机器人左肘 ID 1。画面显示一个上下控制区，掌心向上移动时目标增大，向下移动时目标减小；反向关系可在界面切换。

其他关节维持已确认的起始姿态，底盘停止。先只在原标定范围内取一小段活动区间，确认方向、停止与速度正确后再扩大。

这一步验证识别、映射、网络、背包、真实舵机的端到端控制流程。这里没有舵机真实位置反馈，界面只能显示目标和软件执行状态。

### 第二步：双手控制六个上肢关节

| 操作输入 | 左臂目标 | 右臂目标 | 原六轴字段 |
| --- | --- | --- | --- |
| 掌心上下位置 | 肩抬臂，ID 4 | 肩抬臂，ID 34 | `left_lift` / `right_lift` |
| 掌心左右位置 | 大臂前合拢，ID 3 | 大臂前合拢，ID 33 | `left_upper` / `right_upper` |
| 拇指与食指的开合程度 | 肘弯曲，ID 1 | 肘弯曲，ID 31 | `left_elbow` / `right_elbow` |

左右手分别对应机器人左右臂。水平移动作为合拢角的控制输入，方向分别标定，不需要推算真实三维手部位置或做机器人逆运动学。显示镜像与控制坐标分开处理。

第一版覆盖的是已有标定的六个上肢关节。原固定槽位 ID 2/32、腰等其他关节若要加入，需要补标定并修改接收端的固定/动态槽位处理，不能只在界面增加一个选项就宣称支持。

## 特征到关节目标的转换

1. 掌心位置取手腕及掌根关键点的平均值，减轻单点抖动。
2. 在画面上设置控制矩形，记录横向、纵向控制端点，将位置归一化为 0～1。
3. 手指开合使用 `distance(4, 8) / distance(5, 17)`，即拇指尖到食指尖的距离除以掌宽。距离采用像素尺度或保持横纵比例一致的坐标，避免画面宽高不同造成失真。分别标定合拢、张开的读数后归一化。
4. 将归一化结果映射到所选轴的目标范围，再走原来的角度到舵机原始位置映射、限位和运动平滑。

映射公式为：

```text
u = clamp((当前特征 - 特征起点) / (特征终点 - 特征起点), 0, 1)
目标角 = 角度起点 + u × (角度终点 - 角度起点)
```

端点过近的标定必须拒绝。这里的“目标角”沿用原六轴接口定义，不是把手指角度直接写成舵机角度，更不是直接发送 PWM。

原接口的肘角定义为 0～180，肩抬与大臂合拢为 0～90；这些是软件标定输入范围，不等于任意姿态下均可安全跑满的机械范围。首次联调使用更小的目标区间。

不使用单目估计的绝对深度控制关节。画面中手的前后移动不作为新增自由度。

## 复用与新增的代码边界

从 `robot_integration/backpack_arms6` 复制一份独立功能目录，保留原姿态控制入口。

建议新增：

- `hand_capture.py`：摄像头取图、Hand Landmarker 推理、手部身份与采样时间。
- `hand_mapping.py`：位置/开合计算、用户控制区标定、六轴目标与有效标记。
- `hand_pc.py`：预览、模式选择、开始/暂停、目标显示与现有发送器衔接。

优先复用：原网络发送与接收、六轴 `arm_config.json`、`arm_follow.py`、`robot_motion.py`、舵机编码和串口所有权机制。识别线程只保留最新观测，不堆积待执行动作。

真正接入前，需要用原完整源码核对消息字段、输入来源校验和每轴有效性规则。手势输入不能沿用人体几何特有的“低肩时冻结合拢轴”等规则；应单独定义手势模式的有效性。若协议需要新增输入来源，两端一起升级并保留版本校验。

统一只允许姿态跟随、手势跟随、动作回放中的一个模式拥有上肢目标。模式切换先暂停，避免两个程序同时占摄像头或两个接收程序同时占串口。

## 控制与停止行为

- 启动默认 OFF，预览时不驱动。操作者点击开始并完成准备后，才允许输出。
- 第一版通过界面开始、空格暂停，手指开合只负责肘目标，避免与启停含义冲突。
- 保留原约 20Hz 调度、限位、速度和加速度限制；不为手势功能擅自修改用户此前满意的机器人跟随速度。
- 手部特征做适度平滑和小死区；连续推理只接受新的摄像头帧。重复旧结果不刷新采样时间。
- 单手丢失时立即停止更新对应臂目标；首次版本可选择任一所需手丢失即整体暂停。持续丢失、数据超过原 350ms 新鲜度限制、断网、摄像头异常时解除使能，恢复后手动开始。
- 不能靠数组顺序区分左右手。标定时确认人体自身左右，跟踪期间身份不确定或交叉遮挡时暂停受影响目标。
- OFF 表示停止发送新目标，已发送的短时舵机轨迹可能完成剩余约 50ms；不自动回零，也不自动释放力矩。
- 原程序无真实位置回读。接收端重启后仍按原说明人工恢复已标定基准，不能从界面目标推断机器人当前实际姿态。
- 第一版底盘停止；手势控制上肢稳定后再考虑与原底盘控制组合。

## 最短开发与验收顺序

| 阶段 | 工作 | 验收点 |
| --- | --- | --- |
| 1 | 找齐最终六轴源码与配置，先做电脑手部预览 | 单手/双手关键点稳定，左右无误，无机器人输出 |
| 2 | 加单手到左肘目标映射，接预览接收端 | 目标连续变化、范围受限，丢手与空格暂停生效 |
| 3 | 接原机器人执行链路，小范围测试左肘 | 方向正确、无突然跳变，断网后按预期停止新输出 |
| 4 | 扩展双肘，再加入双肩抬臂及合拢 | 六轴映射分别正确，双手互不串臂 |
| 5 | 整理控制区标定、启动入口和操作提示 | 连续展示多次，记录丢手、卡顿和人工干预情况 |

若原六轴完整源码、Python 环境和网络仍可直接使用，可按约 2～3 天安排首轮预览及实机联调；这是开发估算，原链路恢复和现场调参另计。

代码验收应覆盖标定端点/越界、不同画面宽高下的距离比、左右身份变化、过期帧与断线、原舵机映射和固定槽位。测试通过后仍需上述实机验收，不能用模拟串口结果替代运动效果。

## 新板卡的后续作用

FS01 恢复启动并验证输入/输出接口后，可先承担按键启停、状态显示或控制消息转发；这些仍需要单独开发板端程序及接口适配，不是接上 USB 就能直接代替机器人驱动器。

若以后要求脱离电脑，再评估将手部模型转换到板载 NPU，或在板端 ARM CPU 运行兼容推理框架。现有健身项目的人体 17 点模型没有手指关键点，不能直接用于这套手部开合控制；板端模型兼容性、性能和相机驱动均需重新验证。

第一阶段交付应定位为“摄像头手势连续控制六轴上肢”。新板卡移植作为下一阶段目标。
